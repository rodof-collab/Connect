# CONTRIBUTING — как мы работаем в этом репозитории

Договорённости команды. Это не формальность, а наш контракт:
часть пунктов ниже принудительно включена защитой ветки main.

## 1. Ветки и main

- `main` защищён: прямые пуши запрещены, любые изменения — только через Pull Request.
- Начало работы:
  ```bash
  git pull                     # свежий main
  git switch -c <ветка>        # своя ветка от него

- Нейминг веток обязателен:
Префикс  - Когда                            - Пример
feature/ - новая фича                       - feature/bot-handlers
fix/     - исправление бага                 - fix/config-env-parsing
chore/   - рутина,структура конфиги и тд тп - chore/project-structure
docs/    - только документация              - docs/contributing
Имя: строчные буквы, слова через дефис.
Одна ветка = одна задача. Не смешиваем «хендлеры» и «заодно переписал базу».

## 2. Коммиты
Стиль — Conventional Commits, тип на английском:
feat:, fix:, chore:, docs:, refactor:, test:
Примеры хороших сообщений:
- feat: add /start handler with welcome keyboard
- fix: read DATABASE_URL from env instead of hardcode
Плохо:
- fix fix fix
- asdf
- пофиксил
Коммит = одна логическая правка; мелкие коммиты лучше одного гигантского.

## 3. Pull Request и ревью
Минимум 1 апрув от человека, не являющегося автором — без него мердж невозможен, это включено в защите main.
Новый пуш в ветку сбрасывает апрув: допушил правки после ревью — попроси посмотреть заново (это тоже включено принудительно).
В описании PR: что сделано и как проверить (команды запуска).
Мерджим только Squash and merge: в main одна задача = один аккуратный коммит.
После мерджа ветку удаляем (GitHub предложит сам), все делают git pull.
PR тимлида ревьюит: <Шаланин Лев>. Остальные PR смотрит тимлид или любой незагруженный участник.
Срок ревью — до двух суток, чтобы не блокировать друг друга.

## 4. Чему не место в репозитории
.env, токены, ключи, пароли. Для примера конфигурации — .env.example без секретов.
.venv/, __pycache__/, кэши, архивы, дампы БД.
Секрет, попавший в коммит, считаем скомпрометированным: отозвать/перевыпустить и сообщить команде в тот же день.
## 5. Гигиена
Окончания строк: LF у всех, это обеспечивает .gitattributes — не воюем с ним.
Зависимости: добавляем в pyproject.toml (и дублируем пин в requirements.txt), не тащим руками в venv «на время».
VS Code при открытии проекта сам предложит расширения из .vscode/extensions.json — соглашаемся.
Локальный запуск: создать venv, pip install -e ., скопировать .env.example в .env и заполнить.
## 6. Аварии и изменения правил
Аварийный фикс: ветка fix/... + максимально быстрый PR, апрувит любой доступный участник (минимум один по правилам). Обходов защиты ни у кого нет.
Правила из этого файла меняются только решением всех четверых и тоже через PR.

## Работа с базой данных и миграциями (Alembic)

Наша база данных PostgreSQL — это единый источник истины для всей команды (и для преподавателя). Чтобы избежать рассинхрона, мы строго соблюдаем три правила:

1. **Модели и миграция — в одном PR.**
   Если ты изменил SQLAlchemy-модель (добавил поле, таблицу), ты **обязан** в этом же коммите/PR создать миграцию:
   ```bash
   alembic revision --autogenerate -m "describe changes"
   ```
   Миграция должна быть проверена глазами перед коммитом (autogenerate иногда ошибается).

2. **Затянул чужие изменения с моделями — обнови локальную БД.**
   Если ты сделал `git pull` (или переключился на ветку), где были новые модели/миграции, первым делом выполни:
   ```bash
   alembic upgrade head
   ```
   Иначе локальная база будет отставать от кода, и тесты упадут.

3. **Ручных `ALTER TABLE` не делает никто и никогда.**
   Запрещено заходить в базу через pgAdmin, DBeaver или консоль и вручную менять структуру таблиц.
   Любое изменение структуры БД фиксируется только через код моделей и миграции Alembic.
   *Почему:* если база меняется «руками», Alembic об этом не знает. При следующем `alembic upgrade` или в CI всё сломается.
